# The Lifecycle of a Request

This document follows one request from the moment it reaches a seat to the moment a reply leaves, and says what happens at each checkpoint when something is refused.

Maturity labels used here: **In production** (built and used on a paying client's seat), **Built, not yet in client use** (merged code that no paying client's seat uses yet), **Specified, not built** (designed, not built). Unless a step says otherwise, everything in the ordered checkpoints is in production.

## How a request arrives

A request can reach a seat in five ways.

- **Email through a mailbox the client owns.** The seat checks the client's own mailbox every 45 seconds for new mail, for example in the client's Microsoft 365 tenant. In production.
- **Email through a hosted mailbox.** The email service sends a signed notice to the seat.
- **A connected assistant app**, through SMD's console. Built, not yet in client use.
- **A chat direct message.** Built, not yet in client use.
- **A scheduled routine** that the seat configuration authors.

## The ordered checkpoints

These checkpoints run in this order. Each says what happens when the request does not pass.

1. **Arrival check.** A message delivered to the seat must carry a valid signature from the sending service, no older than 5 minutes. If the signature is missing, wrong or stale, the message is rejected before the agent does any work.
2. **Wake guards.** In order: is the seat paused, or has it reached its daily limit on wake-ups; does an authored rule exclude this trigger; is this trigger still in its cooldown for this record. If any applies, the message is accepted but the agent is not woken, and an audit entry records that it was suppressed.
3. **Second verification.** Every delivery is checked again for its signature, its freshness, and whether it is a repeat. Forged, stale or repeated messages are dropped.
4. **Sender authentication.** On the hosted-mailbox path, the sender's address must pass standard email authentication. A message that fails is not dropped. It is treated as coming from an unknown outside sender (see the next step), and there is nothing to reply to.
5. **Sender check.** Two authored lists decide who the sender is. The roster lists the people the Operator works for; a message from someone on it is treated as internal and trusted. The administrator list holds exact addresses only. A message from anyone else has its content placed in a fenced block marked as untrusted, and the whole turn is marked tainted. The content is fenced: no reply is relayed to that sender, the sender is told nothing, and there is no send, commitment or delete on that turn. The agent may still read and draft. The arrival is recorded. If the seat's configuration cannot be read, every sender is treated as unknown.
6. **Choosing the skill.** There is no separate classifier. The trigger that the message arrived on picks a skill. The agent is told plainly what authority the sender has. Some skills are reserved for administrators; a person who is not an administrator who asks for one gets a short decline. A skill the seat has not switched on cannot be read at all. Skills guide the agent; they are not a sandbox. The checks that follow are what enforce limits.
7. **The checkpoint before every tool call.** Before any tool runs, code checks, in order: removes any approval the agent tried to forge; stops everything if the seat is paused; refuses tools to any process that is not the seat's main agent; keeps file access inside authored folders; checks the limit against its ceiling; scans drafts; scans sends; checks the final rendered message; and obtains a single-use grant from the broker. If any check cannot run, the call is blocked. The agent is told it was blocked.
8. **Each tool has a kind of action.** Every tool name is looked up in one fixed registry that gives it a kind of action, such as read, internal write, send, commitment or destructive. A tool that is not in the registry is refused and never runs. Banned tools are refused before any policy is read. A connector whose own list of tools disagrees with the registry stops the seat from starting.
9. **Limit check.** The seat reads the limit written for this kind of action on this seat, with any client change to a limit setting held at or below the agreed ceiling. Then it applies the taint rule (below). Then it decides. A refusal is returned to the agent with a reason. If the limit check itself fails, reads are allowed and everything else is refused.
10. **Recipient check.** A send the Operator starts on its own is classed by who receives it: the client's listed staff, one of the client's listed customers, a listed vendor, or anyone else (an outside party). A recipient that cannot be resolved is never treated as more trusted. A send to a mix of recipients takes the most restrictive kind of action. A send that names another person as the sender becomes a send-as request (see the delivery paths below).
11. **Content gates.** See the section on content gates on outbound messages.
12. **Delivery.** See the section on delivery paths.
13. **Audit write.** One audit entry is written per tool call, as the call happens, not once at the end of a request; model calls and sub-tasks get their own entries too. Each entry records who acted, in what role, with which skill, against which record, digests of the input and output, the limit, the outcome and the duration. It does not store the message text. The broker stamps each entry and chains it to the one before.
14. **Request notice to SMD.** For each request from a listed person, SMD's operations mailbox receives one request notice. Kinds of notice: replied, no reply, queued job done, kind of queued job not yet proven, a person wrote again on a held job, and follow-up. A notice shows who asked, the subject, the request's own words and the first reply, so SMD operations staff do see the text of requests and replies. SMD's console itself stores only counts and keys.
15. **No-answer check.** If 30 minutes pass with no reply sent, no queued job started and no reply held, SMD is paged with a "no reply" notice. It keeps checking for 24 hours. An hourly health check uses the same 30-minute threshold. A health check that cannot read is itself reported as a problem, never as all clear.

## The taint rule

A turn that took in content from an unknown or untrusted source is tainted. The content is fenced. On a tainted turn, the agent may still read and draft. There is no reply to an unknown sender, and no send, commitment, delete or code run on that turn.

There are three narrow exceptions written in code. Each allows only a message to the client's own people, where the recipients were fixed by code or by authored settings rather than chosen by the agent:

- a scheduled message whose recipients were fixed before the turn began, going only to the client's own staff;
- after the agent read web pages through its sealed web reader, an email whose every recipient is one of the client's authored administrators;
- the in-thread reply path, where trusted code relays a draft only to the original rostered sender.

In each exception, the limit written for that kind of action still applies, and every content gate still runs.

## Delivery paths

| Path                     | How it works                                                                                                                                                                                                                                                                                                                                                            | Maturity                                                                                                                                      |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Reply in the same thread | The agent writes a draft. Trusted code relays it only to the person who first wrote in, only if that person is on the client's list, after running the gates again and a rate limit                                                                                                                                                                                     | In production                                                                                                                                 |
| Send on its own          | A send that clears the limit, recipient and content checks is carried out by the broker, which checks the recipients again. Allowed only where a routine is authored to handle it                                                                                                                                                                                       | In production for listed staff, the client's listed customers and listed vendors. Built, not yet in client use for anyone outside those lists |
| Drafts for a person      | The send is blocked and the agent writes a draft. A person sends it from the client's own system                                                                                                                                                                                                                                                                        | In production                                                                                                                                 |
| Asks first               | The withheld message is stored, tied to the person and the conversation. On approval, the stored message, not anything new from the agent, is scanned and sent. Each approval is used once. Asks first applies to sends, to commitments (approved by an administrator's written instruction), and to one kind of destructive action where every item affected is listed | Built, not yet in client use                                                                                                                  |
| Send as a staff member   | The Operator only proposes it. The broker emails the exact draft to the named person and sends it only when that person approves by email                                                                                                                                                                                                                               | Built and set up on a client seat; client use not established                                                                                 |
| Files on a reply         | Only to an authored list of recipients, after three independent checks, with an optional SMD review hold                                                                                                                                                                                                                                                                | In production                                                                                                                                 |

Whether the Operator may send on its own is set per kind of action and per routine. It is not one global switch. Where a routine's limit setting is "Prepares it for you", a person sends.
