# Pitch Practice Feedback Rubric

These are the headings the seat uses when it steps out of the buyer's role and gives feedback on a practice pitch. Each heading says what a good answer does and the common miss. Every fact is anchored to a document and section of the product library, and the library is the only source of product truth.

## Opening and plain language

- A good opening leads with the outcome for the business: a worker that takes on the connecting work between its people and its systems, built and run by SMD. See how-the-operator-works.md, "Before and after: what changes for the business".
- It describes the Operator in plain words a busy owner can repeat, as one worker configured for one business. See what-it-is.md, "Definition".
- Use "solution" when talking about what the business gets, and keep "system" for a specific tool the business already uses.
- Common miss: opening with "AI employee". It lowers trust and raises the fear of replacement. Lead with the seat and the outcome; the AI stays downstream.
- Common miss: jargon about agents, models, gates and runtimes before the buyer has asked how it works.

## Accurate to the product reference

- A good answer says only what the library says, and can name the document and section it came from. It describes what the Operator can do as a capability SMD configures for the client, in the present tense. See what-it-is.md, "How to read the labels".
- Precision on the record: it is tamper-evident, with stated limits, never tamper-proof. See isolation-and-data-custody.md, "The audit record".
- Precision on approvals: commitments and deletions never run on the Operator's word alone. See permission-model.md, "Ceilings from least to most restrictive".
- Precision on memory: it keeps the working preferences each person states and the standing rules an administrator confirms, and a person corrects it by telling it. It does not learn voice from samples; voice is an authored specification. See memory.md, "Learned working preferences", "Administrator corrections" and "Ownership, export and visibility".
- Common miss: saying nothing about a client's requests ever reaches SMD. The accurate line is that SMD's console never shows business content, client files are handled only by AI agents (the client's Operator, and SMD's agents in a workspace sealed to that client), and a request notice with the requester's words reaches SMD's operations mailbox. See isolation-and-data-custody.md, "What SMD can see beyond the console".
- Common miss: claiming a SOC 2 or ISO 27001 certification of SMD's own, or a documented zero-retention arrangement with the model provider. The library states neither. See isolation-and-data-custody.md, "Model and provider posture".

## Objectives before problems

- A good answer asks where the business is trying to go before talking about what is broken, then shows how the Operator gets it there.
- It ties the work to the business's own objective, with the business's systems unchanged and still the record. See how-the-operator-works.md, "Before and after: what changes for the business".
- Common miss: listing pains and promising to fix them before the buyer has said what they want to achieve.

## Collaborative, not diagnostic

- A good answer treats the buyer as the expert on their own business. We build the worker; their people teach it how the business runs. See how-the-operator-works.md, "One worker, configured for one business".
- It describes onboarding as work done together: the client decides, SMD records. See managed-service.md, "Onboarding phases".
- It never claims to know what this prospect's business needs before the conversation has shown it.
- Common miss: "we audit your operations" or "we tell you what to fix". That is the diagnostician's voice, not the guide's.

## Competes with a hire, not software

- A good answer frames the Operator against the next hire, a coordinator or an assistant, never against a software subscription. See how-the-operator-works.md, "One worker, configured for one business".
- It explains that existing tools are things the Operator connects to, not things it replaces. See what-it-is.md, "Definition".
- It names the managed service as half the offering: SMD builds, runs, watches and changes it. See how-the-operator-works.md, "What managed means".
- Common miss: comparing feature lists with a chat assistant or an intake tool the buyer already has. Once the Operator is filed next to a software subscription, the conversation is lost.
- Common miss: promising that nobody is replaced. The library says only that it is sold against the next hire and that the client's people judge the work.

## Capabilities, stated straight

- A good answer describes what the Operator can do as a capability SMD sets up for the client, in the present tense, the way the site does. See built-versus-planned.md, "How to use this page".
- When the buyer asks what a client runs today, it answers plainly from the library. For example, the law-firm pack, email in the client's own mail tenant and queued jobs are running for a client today; the client level dial and chat are built, set up per client; texting and the other industry packs' skills are configured per engagement. See built-versus-planned.md, "Running for a client today", "Built, set up per client" and "Configured per engagement".
- It is straight about references: one industry pack is running for a client today, on one paying client's seat. See what-it-is.md, "Industry packs".
- Common miss: telling a buyer the Operator cannot do something, or that it is not available, because no client runs it yet. If SMD can configure it, it is a capability.
- Common miss: promising a start date for something SMD has not yet set up for any client. The capability is real; the timing is agreed per engagement.

## Boundaries stated correctly

- A good answer states limits as settings the client writes, not as the product's fixed identity. Unset means refused, and the Operator cannot raise its own ceiling. See permission-model.md, "Rules that hold everywhere".
- "Drafts for a person" is one limit the client can choose, not what the Operator is. See permission-model.md, "Ceilings from least to most restrictive".
- For the law example, the line is paralegal and coordinator work, never legal judgment, advice or representation. See what-it-is.md, "A seat at work: one example".
- It names what no setting turns on: the Operator never moves money. See permission-model.md, "The banned list".
- Who may pause it: a principal, and only where the agreement hands that area to the client; otherwise the client asks SMD. See client-controls.md, "Managed and client-operated controls".
- Common miss: "we don't do legal work". That is inaccurate and undersells the product.
- Say: paralegal and coordinator work, never legal judgment, advice or representation.
- Also a miss: "it never sends" or "it never moves a date", stated as identity rather than as a setting.

## No prices, no timeframes

- A good answer gives no amount of money and no fixed duration for any phase. Pricing is set per engagement. See what-smd-commits-to.md, "How to read this document".
- Onboarding phases end on proof, not on a calendar date. See managed-service.md, "Onboarding phases".
- Notice periods in the standard agreement may be quoted as what the agreement states, never as a delivery promise. See what-smd-commits-to.md, "How to read this document".
- Common miss: naming a figure to answer "what does it cost", or promising when work will start or finish.

## Speaks as the firm

- A good answer speaks for SMD as "we" and "our team", never "I" or "the consultant".
- It names SMD Services as the firm that builds and runs the Operator. See what-it-is.md, "Definition".
- Common miss: speaking as a lone contractor, or calling the Operator by a personal pronoun that suggests it is a person.

## How feedback is given

- Feedback uses only the headings above, in that order, and skips a heading that the pitch did not touch.
- Under each heading it names what went well, then what was inaccurate or off-message, then what to say instead.
- Every correction carries a citation: the library document and the exact section it comes from.
- A point the library does not cover, such as pricing, is not judged; the representative is pointed to SMD at team@smd.services instead. See what-smd-commits-to.md, "How to read this document".
