## What broke

**The finding that stands.** At 2026-08-11T14:03:14.543Z a message left `pilot-smokeball@agentmail.to` addressed to `scott@smd.services`, subject `[Deadlines] Escalator woke but Smokeball connector unavailable, 2026-08-11`. Its body stated that the Smokeball connector was unavailable, that no ACK codes were derived, and that no alert was sent. #2258 records all three as false.

The seat did not send it. #2258 rules out every governed path by name: the agent loop (the seat's gateway log has exactly one line between 14:03:05 and 14:03:33, the API call at 14:03:33.907), any audited tool send (no audit row at that timestamp, unscoped over a 44-row window of which 26 were non-session-attributed, so the query demonstrably surfaces orphans), the reply relay (AgentMail's record shows `POST /messages/send` on a new thread with no `in_reply_to`, which the relay does not use), confirm-dispatch (`CONFIRM_SEND_DISPATCHED`: zero rows ever on this seat), the job plane (`jobs` table: zero rows ever), cloud routines (one, disabled, unrelated repo), and a local Claude session (two transcripts contain the body text, both as mailbox reads). Evidence `vfy_01KZRS2SQBJMWRPY5T4KZHYNGG`.

By elimination, something holding `AGENTMAIL_API_KEY` called `/messages/send` on the seat's inbox directly. #2258's working assumption is internal test traffic from another host. AgentMail stores no provenance (no key id, no source IP, no user agent), so **the actor cannot be named from its record** and never was.

**The defect, stated precisely.** Not "someone can send email", which is key possession and no different from a password. The defect is that **the audit log could not answer "did the Operator send this?"** That is the question a law firm asks in a dispute, and the completeness of that record is what the security overview offers them.

**The retraction.** The original filing claimed the deadline escalator fabricated a cause. #2258's header retracts that: the escalator's real final output for that run is on the seat at `profiles/operator/cron/output/cff8fa8bb61b/2026-08-11_07-06-09.md` and is a correct alert (`[Deadlines] 5 need you, 2026-08-11`, five ranked items under real matter names, three admin confirms, one awaiting clearance, carrying exactly the eight ACK codes in the escalation ledger), written to Smokeball memo `12347da3` at 14:04:56 with the eight `fired` events appended afterwards, in the authored order. **There is no narration defect and no fabrication by the agent.** The 14:03 message is a separate artifact that arrived 100 seconds earlier, written from stale late-July context. This note carries the retraction because a backfilled record that repeated the original claim would itself be the fabrication class.

## How it was detected

A human read the message in their own inbox and did not believe it. No instrument fired. The reconciler that compares a seat's sent folder against its audit log was built **as a result of** this incident, not before it, and #2258 records that even after it merged it was inert: `AGENTMAIL_API_KEY`, `OPERATOR_RUNTIME_READ_SECRET` and `OPERATOR_RUNTIME_READ_URL` were absent from the repo's Actions secrets, so every scheduled run since merge hit `HOLD: ... unset`, exited 0 and went green **without scanning an inbox** (`vfy_01KZW7X9ZY0Z3AQA8YF91SJBJA`). It first fired for real on 2026-08-12, raising #2340 one second after the find (`vfy_01KZWAVA2CH4AH97JMPC42SP43`).

That inert period is the second finding and is the reason this note exists: a watchdog that exits zero without observing anything is indistinguishable, on the dashboard, from a watchdog reporting all clear.

## What changed to prevent recurrence

**Landed, detection side.** `operator/bin/reconcile-sends.py` plus `.github/workflows/unaudited-send-reconcile.yml` compare each seat inbox's sent folder against that seat's audit log and open a `prio:P1` issue for any sent message with no matching row. Proven live over 8 inboxes (`vfy_01KZWAVA2CH4AH97JMPC42SP43`). It was given a **read-only** AgentMail key minted for the purpose (`reconciler-readonly`, `inbox_read` plus `message_read` only) rather than the send-capable org key, on the principle that a watchdog observes and does not act. Kill-tested both ways: a message sent directly via the API left no audit row and was flagged by name, while nineteen of twenty broker-audited sends in the same run matched their rows and did not alert (`vfy_01KZW7TR44BFJ5RRX90RMACTZW`).

**Landed, prevention side.** The Captain redirected the work from detection to prevention, and transmit moved **out of the agent process**. The workspace broker (uid 10001) holds the send credential, checks every recipient against the seat's own authored counterparty surface, pins the sending identity from `customer.yaml`, and writes the audit row itself before it answers. Shipped for both mail channels, AgentMail (#2279, overlay#250) and msgraph (#2311, overlay#256), and pinned to the Machine image by #2299. The agent-reachable AgentMail key is now vendor-enforced incapable of sending: an identical request returns 403 `missing_permission` on the gateway key and 200 SENT on the broker key (`vfy_01KZSNBMFF8VY9V3K3XB0MRYJ3`, where the second call is the control without which a refusal could just mean a malformed request). The org-wide key is deployed to **zero** seats (`vfy_01KZWCH7Z2J4HCFRDHZZC6WNQA`); pilot carries only scoped keys, minted by `operator/bin/mint-agentmail-keys.py`.

**Open, stated in #2258 so it is not mistaken for closed.** msgraph has the broker fence but not the vendor one: a Graph app-only token is always `/.default`, every permission its app registration holds, and the agent legitimately needs Graph credentials for the inbound delta poller and its mail tools. Closing that needs a second app registration in the tenant (read-only for the agent, send-capable only for the broker), which is a tenant-admin action.
