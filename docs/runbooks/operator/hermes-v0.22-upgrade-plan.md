## Why this tag

The fleet ran `v2026.9.14` for six weeks. Its locked dependencies carried 78 advisories that the pip-audit gate allowlisted until 2026-11-10, including client-reachable ones in aiohttp, Pillow and mcp, and Pillow and PyJWT are exact-pinned by that Hermes, so no override could reach them. v0.22.5's lock carries the fix for every one of them except brotlicffi, which `operator/requirements/hermes-security.in` overrides (PYSEC-2026-4323, 1.2.0.2 to 1.2.1.0). The allowlist is empty after this promotion.

## What changes in the image

- **The Hermes venv runs on Python 3.14.** v0.22 supports only 3.14 (its `uv.lock` supported-markers are `python_full_version >= '3.14'`; its tree's `.python-version` says 3.14). The interpreter is copied from `python:3.14.10-slim-trixie`, pinned by index digest, to `/opt/python3.14` (world-readable, never under `/root`, so the non-root uids can execute it; the 0700 managed-Python crash loop is recorded at `ENV UV_PYTHON` in the Dockerfile). The build asserts every shared library its extension modules link resolves, the hermes uid can run it, and the venv has FTS5, an OpenSSL default verify path and certifi. The broker, connector and medchron venvs stay on Debian 13's 3.13.
- **PyYAML is no longer in Hermes' lock** (Hermes moved to ruamel.yaml). The overlay imports `yaml`, so `hermes-overlay.txt` now pins PyYAML 6.0.3.
- **Hermes' lock overrides its own dependencies' pins** (browser-harness pins `pillow==12.3.0`; the lock resolves Pillow 13.0.0). `hermes_pip_check.py` tolerates exactly the mismatches the lock's `[manifest] overrides` record, the rule Hermes' own installer applies (`pm/pip_check.py`), and `compile.sh` passes the same overrides to its two Hermes-venv compiles.
- **The security gate audits on 3.14 and refuses a near-empty audit.** pip-audit skips every requirement whose marker is false where it runs; a 3.14-marked export audited from 3.13 read as seven packages and reported clean. `pip_audit_gate.py` exits 2 below 100 audited Hermes packages (117 today).

## The staging failure (first attempt, #3567, reverted in #3574)

The first promotion built, passed every repo test, and then failed to come up on smd-staging: `Failed to load plugin 'hermes-smd-overlay': No module named 'yaml'`, `Webhook: aiohttp not installed`, then `No module named 'shared'` in overlay activation. Cause, proven (vfy_01M603AFMR22YB1R1D4E7F8T4Y): `hermes plugins enable` in the root and profile homes ran the v0.22 package manager's admission, which recorded an empty dependency generation under `/opt/data/installs/<key>/` and downloaded a Python and uv into `/opt/data/tools`. From then on `pm.environments.activate_dependencies` removed the image venv's `site-packages` from every hermes process's `sys.path`. The second attempt removes both `enable` calls, selects the overlay by writing the keys the loader reads (`hermes_cli/plugins_discovery.py` `gate_manifest`), turns lazy installs off in every home, purges exactly that state if a failed boot left it, and refuses to launch a gateway while any of it remains. It is proven on `operator/bin/boot-harness`, a throwaway Machine off every seat, before it reaches one.

Largest `state.db`: pilot-smokeball, 630 MB.
3. **Before merge.** A Fly volume snapshot per seat from the day; `fleet hold` on scott, brokery, captain-mark and ashton-price ("#3564 soak, max 24h"); peer sessions told that client-seat releases pause for at most 24 hours, and that their hotfix lane is reverting this PR.
4. **Merge.** CI builds the image; release-tick rolls smd-staging, then pilot-smokeball. The in-image self-test verifies `hermes_sha` and the standalone decision; a failure rolls the seat back.
5. **Staging, as a client would.** Real mail with an image attachment gets a reply; an MCP tool turn over HTTPS; a connector that reads a Fly-only secret; `curl /p/<other>/` returns 404; a managed cron fires and only the expected stores tick; `hermes config get` returns each pinned row above; the webhook toolset list equals the authored list; a medchron dry run (no paid run); migration time from the boot log. Each check is recorded with `crane_verify`. Any failure means revert the PR and re-prove; never patch forward on live seats.
6. **Client seats.** Unhold scott, brokery and captain-mark; one tick; read back heartbeat sha, the standalone decision and a cron firing. Then ashton-price in a window with no running medchron or litigation job, with migration time scaled from staging under the 600 s lease.
7. **Bless.** `hermes-release-watch.yml` reports the fleet current; the tracker and the four watch issues close citing verify ids.

## Rollback

Revert this PR on main: the next release builds the `v2026.9.14` image and the holds lift. The pip-audit allowlist stays valid to 2026-11-10 for exactly this case. The `state.db` migration (schema 30 to 32) is the one state change an image swap does not undo. Gate 2 proved `v2026.9.14` reads, searches and writes a migrated database, so an image swap is the rollback; the Fly volume snapshot from gate 3 is the backstop if a seat's own database disagrees with the synthetic one.
