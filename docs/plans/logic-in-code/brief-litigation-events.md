# Workstream W6 `litigation-events` (wave 2; runner; the `jobs` rename #3734 is on main, so paths are `operator/runners/jobs/jobs/...`)

Mechanism 6: events in, status out. Today the model picks each litigation defendant's STATUS from a 14-value enum with no source field, while dismissal, settlement and default have no dated field at all; code then reads the free-text notes with regex to correct a no-answer status (#3684 was that patch). The firm's status list is the deliverable; a wrong status there is what the firm sees.

## Build

1. Schema: defendants carry `_DATED` `dismissed`, `settled`, `default_entered` beside `served`, `answered`; `sent_for_service` becomes a LIST of `_DATED` (code takes the max); add `court_dates: [{date, event, _REF}]` at case level (code picks the earliest `>= today`; `next_court_date` is derived, not asked). REMOVE `status` from what the model returns (keep the enum in vocab for the derived value). Prompt COMMON loses the "next one AFTER today" and "most recent request" rules and gains "report every dated event you find, each with its document".
2. `defstatus.derive(d, today) -> status`: one rule table from the dated events: dismissed > settled > (default_entered AND answered, neither undone) = Unclear > default_entered > answered (answered-original when the flags say original/amended) > served with no answer > out_for_service yes > not served. Keep `stated()`/`contradiction()` as the note cross-check (a note contradicting the derived status still holds, NOTE_RULE). `to_state` sets `status = derive(...)` and records `status_from: derived`.
3. Gates: every event date needs a source (`_date_rules` already); add "status not derivable" (events contradict with no dates) as Unclear, never a guess; keep the existing defendant rules; the every-rule-can-fail table gains the new rows.
4. Verdict paths: `defendants[<index>].<field>` built by code (the index of the defendant in the result list); the verify/audit prompts list defendants with their index; `apply_verdicts` LOGS every unmatched verdict (`unmatched_verdicts` in the pass log) and never silently continues; keep accepting the old `defendants[<name>]` form for one release with the same logging.
5. `firm_role` invalid -> Unclear + flag (no default to plaintiff).
6. Discovery12: drop `"not yet due"` from `RESPONSES` (model returns yes / no / unclear); `to_result` sets `not yet due` iff response is `no` or `unclear` with no response date AND `due.date >= today`; `carry._stale` unchanged; `findings` unchanged.
7. Update mode: the model returns CHANGES only (fields an arrived document changes, each with its document); `update.guard` merges onto the prior; TAIL rewritten; `passes.reguard` unchanged.
8. Baseline seeds: `baseline.def_status` keeps mapping hand-run text (the seed has no events); a seeded status is marked `status_from: seed` and a later read with events overrides it by derivation.
9. Tests: `test_litigation_defstatus.py` gains the derive table (every precedence, every undone negation, the Unclear conflict); schema tests; `apply_verdicts` logging (a verdict naming an unknown index is logged, the result unchanged); discovery12 not-yet-due derivation (due tomorrow -> not yet due; due yesterday with no response -> no; unclear stays unclear); update changes-only merge; one mutation per rule (e.g. remove the `>= today` comparison, remove the default-vs-answer conflict rule) caught. Full runner suite green (`cd operator && python -m pytest runners/jobs/tests -q`, about 3,400) plus ruff, pyright ratchet, function-size ratchet, `npm run verify`.
