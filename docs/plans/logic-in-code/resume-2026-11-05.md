## Rule 1: everything that can refuse or change what the firm sees ships switched off, per seat

Top-level `customer.yaml` key, authored per seat, absent on every seat until the proofs need it:

```yaml
logic_in_code:
  printed_source_check: observe # or enforce
  post_record_derivation: observe # or enforce
  conflict_fence: observe # or enforce
  fixed_wording: observe # or enforce
```

- Absent means `observe`. A present value that is not one of the two is `enforce`, because an unreadable switch must not hold a door open. This is the rule of `operator/connectors/smokeball/smokeball_connector/resolution_mode.py`; read it first. `matter_resolution_mode` stays as it is.
- `observe` records exactly what it would have refused, in the mechanism's own audit row, then behaves as today.
- Read fresh on each call, never cached in a module. The bootstrap validator and `sections-persona-skills.ts` / the customer-config parity test both accept the key, with fixtures and the content hash re-pinned.
- No PR in this program edits a seat's `customer.yaml`. The lead authors `enforce` on the pilot, and A&P only after the Captain's yes.

## Rule 2: code first, skills after, in separate PRs

A skill that passes a new argument to a connector that does not have it yet is refused by argument validation, and the connector ships in the jobs bundle while skills ship in their own artifact, so they can land apart. Each of #3752, #3753 and #3742 therefore splits:

1. **Code PR.** Connector, overlay and broker accept the old arguments and the new ones, and an old-style call behaves exactly as today. Merge this first.
2. **Skills PR.** The `SKILL.md` edits, version bumps and skill-pinned tests. Do not merge it. It waits until the lead has read the code off every seat and proven it on the pilot.

A test that pins a skill's new text moves to the skills PR.
