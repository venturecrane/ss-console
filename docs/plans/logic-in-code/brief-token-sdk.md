## Facts you build on (all verified 2026-11-04, cite them in your PR)

The wrapper uses `functools.wraps`, so MCPServer derives the inputSchema from the original signature (`inspect.signature(fn, eval_str=True)` in mcp's `func_metadata`); a `__signature__` set on the wrapper is honoured and stops the unwrapping. Tool modules use `from __future__ import annotations`, so build the new signature from `inspect.signature(fn, eval_str=True)` evaluated in the ORIGINAL function's globals (otherwise string annotations resolve in the SDK module and raise). ## Build

1. SDK: `ConnectorServer.tool(..., requires_resolution: Callable[[dict[str, Any]], str | None] | None = None)`. When set, the registered wrapper: carries the augmented `__signature__`/`__annotations__`/`__doc__`; pops `matter_resolution` from kwargs; resolves the target matter with the callable; in `enforce` mode calls `verify` before dispatch and `consume` after the tool returns without raising; in `observe` mode records a `would_refuse` row when verify would refuse (missing, unknown, expired, bound elsewhere) and dispatches anyway; raises `ResolutionRefused`'s sentence as the tool error in enforce. A tool with no `matter_id` resolvable (resolver returns None) is refused in enforce with a sentence saying which argument was missing.
2. Mode: `matter_resolution_mode: observe | enforce` under the Smokeball connector's config block in `customer.yaml` (find where that block is read and validated today; default when absent is `observe` for ONE release, and the validator refuses any other value; the ADR the lead writes will say when the default flips). Expose a small reader the SDK can call (the SDK must not import smokeball_connector; pass the mode to `ConnectorServer` at construction or through a setter the smokeball server calls at startup).
3. `resolve_matter_by_id(matter_id, matter_number)` READ tool in `smokeball_connector/server.py` (or `matter_resolution.py` with registration in server.py): fetches the live matter, mints only when its number equals `matter_number` exactly (two facts), returns the same shape as `resolve_invoice_matter`'s unique verdict; a mismatch returns `none` with the live number NOT echoed (the model must not learn it from a refusal); a fetch failure returns `search_failed`. Add it to EXPECTED_TOOLS, manifest classes (READ), action_classes.
4. Tests: SDK unit tests (signature shows the param and `required`; pop happens; verify/consume order; observe vs enforce; resolver None); connector tests for the new read (unique, mismatch, failure; mock the HTTP tenant as `test_matter_resolution.py` does); conformance schema assertion; validator tests for the key; one mutation (e.g. remove the consume call) that a test catches.
5. Docs: `operator/connectors/_sdk/README` (if any) and the Smokeball connector README/surface doc mention the flag and the new read; `docs/handbook/` has an "if you change X, update Y" table (`docs/handbook/README.md`): check whether the connector tool list is a generated/completeness-checked list there (`tests/handbook-integrity.test.ts`) and update the page if so.
