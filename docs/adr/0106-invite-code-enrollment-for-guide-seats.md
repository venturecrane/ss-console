# ADR 0106: Invite-code enrollment for guide seats

- **Status:** Accepted (2026-11-09)
- **Decider:** Captain (the two contract sentences below, 2026-11-09); mechanism by the agent
- **Amends:** ADR 0055 (the roster, authored as `scope.inbound_allow_from`, is the set of people the seat answers): on a guide seat that switches enrollment on, a person SMD invited joins that set by sending a code, without a reviewed change to `customer.yaml`
- **Builds on:** ADR 0105 and ADR 0090 (the `guide` role, selected by `seat.role`), ADR 0072 (the roster classifier: a rostered recipient is internal), ADR 0094 (`customer.yaml` as built: one publisher, root-owned on the seat), ADR 0044 and ADR 0026 (the agent has no path to widen its own configuration), ADR 0035 (unauthored is fail-closed), ADR 0032 (the webhook router sees inbound mail before any model)
- **Scope:** seats whose `seat.role` is `guide` and whose `customer.yaml` authors `sender_enrollment: {enabled: true}`. Today that is `smd-guide` only. No client seat changes, and no client seat can opt in.

## The contract

1. "A person holding a valid invite code emails the guide seat from an unlisted address with the code in the message. The seat verifies the code in code, before any model sees the message, records that address as an enrolled sender for this seat, sends a fixed welcome reply, and tells SMD. From then on that address is treated like a listed person for this role's work. A wrong, used or expired code gets no reply and enrolls nothing."
2. "An administrator of the guide seat emails (or messages in chat) 'I need a code for <name>'. The seat issues a code tied to that name and delivers it to that administrator. When the named person later connects with it, the welcome greets them by name, and the guide knows their name from then on."

## Context

The guide seat (ADR 0105) answers outside sales representatives. Until now a representative could reach it only after SMD added their address to `scope.inbound_allow_from` in a reviewed PR and the config was published. SMD does not know a representative's address in advance, and a PR per person is the wrong cost for a seat whose whole audience is people SMD chose to invite. The roster is authority, though: who the seat answers is also who it writes to, untainted (ADR 0072), and on a client seat who is listed is the client's own decision. The mechanism has to widen the roster for invited people on this one kind of seat without giving the agent any way to widen it for itself.

## Decision

1. **Opt-in, guide seats only.** A top-level `sender_enrollment` block whose only key is `enabled` (boolean). Both validators (the console's and the overlay's) accept it only on `seat.role: guide`, and every runtime reader requires the role as well. With no block, or `enabled: false`, nothing below exists on the seat (ADR 0035: unauthored is off). `operator/customers/smd-guide/customer.yaml` authors it enabled.
2. **The code.** `SMD-` followed by three groups of four characters, twelve random characters from a 30-character alphabet with no 0, O, 1, I, L or U (about 59 bits). Each code is stored as a per-code salted scrypt hash (n 2^14, r 8, p 1, 32 bytes, 16-byte salt) and compared in constant time against every row. It is printed or sent once and never kept. Each code row carries an id (`c_` plus 12 hex), a label, an optional person name, an expiry of 1 to 90 days, a use limit of 1 to 100 (default 1; a multi-use code with an expiry is a shared pass phrase), a use count and a revoked time. ss-console is public: no code, phrase or hash is committed.
3. **The store is the broker's, on the volume.** `/opt/data/sender-enrollment/` (owned by the workspace broker, group `audit-readers`, mode 2750), bind-mounted for the broker at `/run/smd-sender-enrollment`, the posture of the audit ledger (`/opt/data/audit` to `/run/smd-audit`). `enrolled.json` (0640) lists each enrolled address with its label, code id, time and name; it is the only file the agent uid can read, and it cannot write it. `private/codes.db` (0600, in a 0700 directory) holds the code hashes and the attempt rows used by the lockouts (pruned after 48 hours); `private/lock` serializes every write.
4. **Why the broker and not the exposure-override precedent.** The entitlement store the gate writes (`/opt/data/smd/exposure_override.db`, ADR 0026) can only narrow within an authored ceiling, so the agent-side process may write it. This store widens who the seat answers. `customer.yaml` was made root-owned so the agent uid could not widen its own roster, the structural close of the self-loopback (ADR 0044, ADR 0094); an enrolled list the agent uid could write would reopen that loop. So the broker uid is the sole writer, the agent uid reads the list only, and the codes are unreadable to it.
5. **Redeem (contract 1).** The webhook router (`_enrollment_attempt` in `plugins/hermes-smd-webhook-router`), after the delivery is verified and before any envelope, fence, origin, request card or inbound audit row: on an email to an opted-in guide seat, from a sender who is neither on the roster (authored or enrolled) nor an administrator, whose subject or body carries a code-shaped token, it computes the sender's authentication (aligned DKIM or DMARC, `shared/sender_auth.py`), calls the broker verb `sender_enrollment_redeem` (gateway only), and ends the delivery with no model turn, whatever the outcome. The broker re-checks the opt-in, re-reads the message from the mailbox and refuses if its sender differs from the router's or the code is not in that message's own text, and returns `already_listed` without consuming anything for a sender already on the roster, a domain grant, the administrators or the enrolled list. Then, in order: a seat-wide lockout (20 refused attempts in an hour), an unauthenticated sender (consumes nothing and counts only toward the seat-wide limit, so a forged From cannot lock out the real person), a per-sender lockout (5 refused authenticated attempts in 24 hours), a wrong, revoked, expired or used-up code, and otherwise enrollment: one use consumed and the address appended with the code's name. Every attempt writes one audit row, `SENDER_ENROLLMENT_ATTEMPT`, carrying the outcome, a sha256 of the address, the message id, the authentication reason and the code's id and label when one matched; never the code or a digest of it. On enrollment the router sends the fixed welcome ("Hello <name>," or "Hello,") as a reply in the sender's thread through the broker's recipient-checked, participant-fenced, audited transmit, and emails SMD (the seat's administrators at SMD's own domains) a fixed notice naming the address, the code id and the name. Every refused outcome gets no reply and enrolls nothing.
6. **Admin-issued named codes (contract 2).** The tool `invite_code_issue` (plugin `hermes-smd-enrollment`, toolset `enrollment`, registered only on an opted-in guide seat) takes `name` (required), `days` (1 to 90, default 14) and `max_uses` (1 to 100, default 1). Its class is internal write: it names no recipient, writes the seat's own store, and its one message goes to the administrator who asked, so the `smd-guide` persona authors `internal_write: autonomous`. The tool refuses in code, each with fixed wording: a turn with no verified email origin (a chat turn; on a guide seat no chat id is mapped to an administrator), a sender not exactly on `scope.admins` ("Invite codes are issued only to the guide seat's administrators at SMD Services. If someone needs access, ask SMD Services at team@smd.services."), a tainted turn, and a name that is not plain. The broker verb `sender_enrollment_issue` (gateway only) re-checks the opt-in, the administrator, that the mailbox says that administrator sent the message, and the name rule; mints the code with the name; and sends one fixed-wording reply in the administrator's thread through the fenced transmit (the code, the name, the expiry, the uses, how the person connects, that it is for that person only, and how to revoke it by id). A failed send revokes the code. Its audit row, `SENDER_ENROLLMENT_CODE_ISSUED`, carries a key of the administrator, the code id, the days, the uses and whether it was sent. The model sees only the code id and "sent". The code lives in the administrator's own mailbox, which is the point; the broker's confirm-send rows hold only a digest of the payload.
7. **The name.** Validated in code: letters of any script, spaces, apostrophes, hyphens and periods, starting with a letter, one line, at most 60 characters, no double spaces. Code interpolates it into exactly two places: the welcome greeting, and one platform-stated line in the initiation standing block ("This sender connected with an invite code SMD issued for <name>; address them by that name."). Removing an enrolled address removes its name from the list and from its code row.
8. **What enrollment grants: exactly a rostered sender's standing, never an administrator's.** On an opted-in guide seat the overlay's single roster accessor (`CustomerConfig.inbound_roster`) includes the enrolled addresses, so the router classifies them internal (untainted, origin recorded) and the reply relay, trust and initiation layers treat them as rostered. On the broker side `recipient_policy.authored_policy` adds them to the reply and send fence and `participant_fence.seat_facts` adds them to the internal roster. The participant fence (`operator/workspace_broker/participant_fence.py`) is recorded in that module, not in an ADR; it is unchanged in rule, and an enrolled address stands where an authored roster address stands. The git-authored roster and the single publisher of ADR 0094 are untouched. The broker re-reads the store on every call, so a new enrollment is answered at once, with no restart.
9. **SMD's command line** (the fallback), on the seat as the broker uid: `python -m workspace_broker.sender_enrollment_cli` with `issue` (prints the code once), `codes` or `list` (never the code), `revoke CODE_ID`, `enrolled`, and `remove ADDRESS`. Run as root it drops to the broker uid.
10. **Abuse limits and observability.** The lockouts in decision 5; a heartbeat field `sender_enrollment` (enrolled count, refused attempts in 24 hours, locked), which the console stores per seat and alerts on as guessing (`enrollment_guessing`).

## Lifecycle

The store is on the Fly volume, so it survives a restart and a reprovision by design, like the exposure-override store. A person is removed with `sender_enrollment_cli remove ADDRESS`; a code is stopped with `revoke CODE_ID`. Decommissioning the seat removes the directory with the volume. Root `CLAUDE.md` ("Gone means gone") lists the store as a runtime layer.

## Consequences

- **The broker trusts the gateway's statement that the From was authenticated.** Every other fact (the sender, the code's presence in the message, the opt-in, who is already listed) is re-derived broker-side from the mailbox and the config. A process inside the gateway that holds a valid code could enroll an address whose mail carries no aligned pass.
- **A code pasted into an ordinary message by a listed person, an enrolled person or an administrator reaches the model.** The router acts only on unlisted senders. Nothing is consumed, and SMD can revoke the code by id.
- **Any code-shaped token from an unlisted sender on an opted-in seat is dropped before the model.** That narrows today's unknown-sender handling for that one shape; such a sender got no reply before either.
- **A stranger can trip the seat-wide lockout** and refuse legitimate enrollments for up to an hour. That is the fail-safe direction.
- **The `smd-guide` persona now authors `internal_write: autonomous`**, which the tool's class needs. It is also a CORRECTION to ADR 0105's seat config as merged: the email reply path is itself an internal write (`mcp_agentmail_create_draft` is `INTERNAL_WRITE` in `shared/action_classes.py`, and the reply plugin's `text_delivery.py` synthesizes that `create_draft` call through the trust plugin's own `pre_tool_call`), so with only `external_send_internal` authored every email reply on `smd-guide` would have been refused at the gate. The internal-write tools this opens on that seat: the mail connector's draft and label tools (`mcp_agentmail_create_draft`, `update_draft`, `delete_draft`, `update_thread`, `update_message`), the reply relay's `reply_verdicts` and `reply_bind`, Hermes' own `todo` and `clarify`, the escalation plugin's `escalation_append` and `escalation_reply_ack`, `correction_capture` (which refuses any sender not on `scope.admins` in code), and `invite_code_issue`. Not reachable: `calendar_invite_*` (no Calendar connector), `operator_help_*` (the operator-help skill is not enabled), record-store writes (no record stores) and every connector write (the seat's only connector is its mailbox). This list comes from reading each plugin's registration gate and the seat's config; it is not a probe of a running seat, because smd-guide is not provisioned.
- **Enrolled senders widen who the guide seat answers and writes to.** Only on guide seats, only after SMD issued a code, and each address can be removed.
- **Chat is not built.** The chat allow-list is materialized into the profile and the channel's allowed-users variable at boot (`bootstrap/translate.py`, `operator/templates/ensure-telegram-allowlist.py`, ADR 0033), the runtime reads it once at gateway start, and it rejects an unknown chat id before any plugin sees the message. There is no seat-side store a pre-dispatch hook could consult per message, and chat has no hook before the model equivalent to the email router's. Building it would take a broker-owned chat enrollment list, an allow check that consults it live for an unknown id, and a code-in-chat redeem path that never lets the model see the code. Until then a representative is reached by chat only through a reviewed allow-list PR, and an administrator's chat request for a code is refused with a pointer to email (contract 2's "or messages in chat" is answered by that refusal).

## Amendment (2026-11-10): a non-administrator learns nothing about codes

The owner's rule: the seat never tells a person who is not an administrator that it can generate a code. Decision 6's decline said codes are issued only to the guide seat's administrators, and the chat refusal said an administrator asks by email; both told a representative the capability exists, and the product library's `connecting.md` described how an administrator gets one. Now:

- Every path of `invite_code_issue` that has not confirmed an administrator (an unreadable or switched-off config, a turn with no verified email origin, including every chat turn, and a sender not on `scope.admins`) returns one sentence for the model to send word for word: "Access to the guide comes from SMD Services, at team@smd.services." It names no capability and nothing about the asker's role, and the result carries no refusal for the model to restate. The decision stays in code.
- The `product-guide` skill sends the same sentence for any other question about who makes or issues codes.
- The library describes only how a representative connects with a code from SMD Services. The administrator how-to is in the handbook, `docs/handbook/connectors-channels.md`, "Getting a guide-seat invite code for someone".
- An administrator's request is unchanged: the code is emailed in their thread and the guide replies in one line.

`tests/guide-code-capability-not-disclosed.test.ts` pins the sentence and fails if the tool, the skill, the library or its index again says who makes or issues codes.

## Amendment (2026-11-10): what an enrolled person keeps, and removing it

The guide seat is to let an enrolled sales representative keep notes and leads only they can see (ss-console #3946). Removal used to clear only the enrollment row (decision 9's `remove`), so whatever the seat kept under that address stayed on the volume. This amendment adds the general overlay capability and the removal; it switches nothing on for any seat (a later, separate config change authors the stores on the guide seat).

1. **A record store walled per person.** A store authored with `partition: sender` keeps each person's records in their own directory, `<store path>/<person_slug(address)>/`, with the slug of `shared/person_prefs.py` (a sanitized prefix plus a hash of the whole address, so no address reaches another person's directory by case, a look-alike character or a separator). The owner is the directory, set by code from the turn's verified sender, never written in the content and never supplied by the model. The wall is enforced in the tool handlers (`plugins/hermes-smd-record-store`), keyed by the session id Hermes hands a handler and the strict per-turn verified sender (`SESSION_INBOUND_ORIGIN.bound_this_turn`), not in `pre_tool_call`, which Hermes calls with no session id. A turn with no verified sender (a scheduled turn, a wake, a chat turn) or a sender not on the seat's roster at that moment (authored, or enrolled here) is refused list, read and write with one sentence. List shows only the caller's own directory, and the model-facing tools have no read across the wall. Such a store refuses `owner_field`, `readers` and `writers` (both validators). A store authored `managed: true` refuses the model's write; code writes and reads it through `shared/record_store.py` `code_write`, `code_read` and `code_list`, which name the person explicitly and, for a partitioned store, require that person on the roster.
2. **Per-sender memory can be switched off.** `memory.peer_memory_enabled: false` makes `hermes-smd-peer-memory` register no tool, no hook and nothing in the prompt. Absent keeps every seat as it was; `operator/hermes-smd-overlay/tests/test_authored_seat_registration_unchanged.py` pins, seat by seat, that no authored seat's tools or hooks changed.
3. **Removal purges, and proves it.** `sender_enrollment_cli remove ADDRESS` and the new `purge ADDRESS` delete everything the seat's code keys to that address (`operator/workspace_broker/person_purge.py`, stdlib only): the person's directory in every partitioned store; their rows in `peer_preferences` (`/opt/data/agent-state.db`), in the request index (`/opt/data/requests.db`, their requests and the replies to them), in the held-reply store (`/opt/data/held_replies.db`) and in the help-pointer state (`/opt/data/smd/help_state.db`, keyed by a salted hash); the sent-line label files whose recorded recipients include them (`shared/sent_lines.py` now keeps a sha256 of each recipient for this); and the entries naming them in any scheduled-send envelope, pending or consumed. Rows are deleted with SQLite's secure delete on and the write-ahead log truncated, so their bytes do not stay on a free page. Both commands then read the volume back (`purge --probe ADDRESS`, read-only on its own) and exit nonzero if anything of theirs remains, or if the config naming the partitioned stores could not be read. `purge` works for an address that is no longer, or never was, enrolled.
4. **Who runs it.** The command line runs as root on the seat. A forked child drops to the broker uid and removes the enrollment row (the broker's store); the parent, still root, deletes the files on the agent's volume, which the broker uid cannot reach, through directory descriptors opened without following any link, and hands each database to a child dropped to that file's owner, so root never opens an agent-owned database. Before the row goes, every place is examined; if one cannot be (a run as the wrong uid, an unreadable directory, a planted link), nothing is removed and the command exits nonzero naming it. The row goes first: a turn of that person's still in flight is refused by the store's roster check at its next call, and a write that races the removal is read back and undone, so the purge cannot be undone by a turn that started before it.
5. **Kept by decision (named-retained), not purged:** the seat's session transcripts (Hermes `state.db` and `sessions/` in each profile home), which hold every turn's messages, tool arguments and tool results, so full copies of what the person sent and stored; the mail at the mail vendor; logs and Sentry; volume snapshots; the audit ledger (hash-chained, a hash of an address and no text); the enrollment store's attempt rows (a hash, pruned after 48 hours); Hermes' tool-result spillover files, which cannot be attributed to a person; and request-index rows and sent-line files whose sender or recipients were never recorded or were already nulled by their custody window.
6. **The instrument.** `operator/hermes-smd-overlay/tests_e2e/test_guide_rehearsal.py` drives a guide seat through the webhook router and Hermes' own agent loop at $0 with two enrolled people, then searches every file and table on the seat's volume, the model request log, the captured logs and the broker's record for one person's marker string: every hit must be in the purge set or the named-retained set, before and after that person is purged.
