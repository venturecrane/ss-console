# ADR 0102: Matter files on a staff reply

- **Status:** Accepted (2026-11-02)
- **Decider:** Captain (the ask: an attorney's request for named records must be answered with the records); mechanism by the agent
- **Amends:** ADR 0086 (a new matter-identity seam: the files a reply carries), ADR 0053 (two connector tools), the outbound-attachment rule in `shared/outbound_attachment.py` (a firm's own record to its own staff is exempt from the text read only)

## Context

On 2026-11-01 an attorney at the first client emailed the Operator for five named records on one matter, attached to its reply. The Operator answered, truthfully, that it could not search the matter's documents by name (the file listing returns 500 rows a page with no filter, on a matter with thousands) and that its email could not carry a file. Until now an attachment was never a tool argument and the model never named a file; the only files a seat sent were a routine's workbook and SMD-staged PDFs, both chosen by code.

Of the five records most were scans (image-only, or a garbled text layer), one was 6.67 MB, and two were a few pages inside very large sets: pages 1-4 of a 223-page 3.9 MB file and pages 3-11 of a 2,310-page 413 MB file. The seat has no OCR tool.

## Decision

1. **Find by name, server-side.** `find_files_on_matter(matter_id, name, folder, extension)` (Smokeball connector, READ) pages the matter's whole file listing and filters in the connector: every word of `name` in the file name, a folder name at any depth or a path suffix, an extension. It returns file id, name, extension, folder path, size and dates, and `searchComplete`. The vendor's `Search` parameter is answered from a separate document search index whose matching, lag and coverage we have not observed on a live tenant, so it is not used; the listing is the record. Past 30,000 files the result says the search was partial. A failed page is an error, never "none found".

2. **The model names files; code moves bytes.** `stage_matter_files(matter_id, files)` (Smokeball connector, READ: it writes only the seat's own disk) takes up to nine `{file_id, pages?}`. The connector checks each file's own record names this matter, that it is a PDF, fetches it (streamed to disk, up to 600 MB for a page cut, 25 MB whole), cuts a page range itself when one is named (at most 200 pages), and writes each result to the seat's outbound file spool with its sha256. A file that cannot go is refused by name with its reason; the others still stage.

3. **The reply plugin carries them, under fences the model cannot reach** (`shared/matter_file_reply.py`, `hermes-smd-reply`). From the connector's own tool result, in a hook: the stage is bound to the email that opened this turn, on a Graph seat, whose sender is firm staff. Each file is read back from the connector spool against its sha256, passes the gate's structural PDF check, and goes in 3 MiB chunks into the BROKER's own spool (`attachment_put`), which the agent cannot write and which hashes what it receives. At the reply, after every floor a reply already meets: the same email, firm staff, no device redirect, no bound reply, and one matter (the files' matter is the only matter whose content the session read, and the body cites no other). A refusal clears the staging and holds the reply with the reason, so the model redrafts without claiming a file. A reply carrying files is never queued behind the rate limit, because a queued reply is released without them.

4. **Who is firm staff is authored per seat.** `matter_file_delivery.recipients` (addresses or `@domains`) in customer.yaml. A recipient must be on that list AND on `scope.inbound_allow_from` AND classify INTERNAL (never typed client, vendor or anything else in `scope.outbound_roster`). The connector, the reply plugin and the broker each check. Unauthored, nothing stages and no reply carries a file. This is the per-seat gate: a config block the capability reads, as `vendor_invoice_intake` is, rather than a new exposure class, because the act is a reply the seat already makes to its own staff and the entitlement question is only "to whom may the firm's files go", which is a list.

5. **The broker's reply verb carries files only on this path** (`workspace_broker/msgraph_reply_files.py`). Descriptors are `{name, content_type, handle, sha256}`; the broker re-reads its own copy and refuses unless its hash matches, refuses non-PDFs, encrypted PDFs and PDFs naming active content outside stream data (a scanned page's image bytes are arbitrary and would match by chance), re-vets the fetched sender, drops copied participants who are not staff, and refuses a device redirect. It builds a `createReply` draft on the READ credential, attaches files (inline under 3 MB; above it through the shared upload-session helper `msgraph_upload.upload_large_attachment`, ADR 0101), re-reads the draft (recipients exactly the sender plus the kept copies, no bcc, the body's words present, every attachment's name, type and sha256 exactly as vetted, the bytes fetched back and hashed), deletes it and refuses on any mismatch, and sends it on the SEND credential. The audit row's `attachment_sha256` is the broker's hash of each file.

6. **Three files and 25 MiB per message; more go as further replies.** A request needing more than three files (or more than 25 MiB) is answered with the person's reply carrying the first batch and up to two further replies in the same thread, each with the code-fixed words "Part N of M of the files you asked for, attached: ...". Each is audited (`file_reply_part`).

7. **Scanned PDFs: the text read does not apply to a firm's own record going back to its own staff.** The outbound gate refuses a PDF with no readable text, because what it cannot read it cannot check. That rule stays for every other send. Here the text gate has nothing to catch: it exists for words the Operator wrote or relayed (fabrication, another matter's identifiers, facts reaching an outsider), and a scan the firm filed, fetched by code and returned unaltered to a colleague who can already open it in Smokeball, carries none. What can still go wrong is structural (an active PDF) or a misdelivery (wrong matter, wrong person), and those checks run on every file, scanned or not. Outside the firm nothing changes: this path reaches the firm's own staff only.

8. **SMD can review before files go** (amendment, 2026-11-02, the Captain's ask for the first request). `matter_file_delivery.review: smd` holds every files reply; `review_first: N` holds every files reply until SMD has released N of them, then sends normally, counted from the seat's own reviewed rows that were approved and sent, so it expires by itself. A rejected, expired, failed or still-waiting row counts for nothing (2026-11-02: counting every held row let a rejected first reply release the next one unreviewed). A held reply is written to `/opt/data/matter-file-review/` with who it goes to, the words, and each file's Smokeball id, name, page range, page count, size and sha256; the email counts as answered so a redraft cannot slip past. SMD reads it with `python -m shared.matter_file_review list` and decides with `approve|reject <id> <digest>` as root, which writes a root-owned decision file the agent uid cannot write; the gateway's held-reply sweeper acts only on a root-owned decision naming the row's current digest, sends exactly the held words and broker-spool handles (same hashes), and never sends a row twice. The broker spool keeps files 24 hours, the review window.

9. **Every staged file is a rewrite with its embedded files stripped** (amendment, 2026-11-02, two ordinary A&P records refused on the first live run). A 35-page discharge summary was refused for one embedded file named "Content Credentials" (a 24 KB C2PA provenance item a scanner adds), and a 223-page set for its 97,058 objects, over the reply check's 50,000 bound (a size bound, not a threat sign; page cuts of it passed). So `stage_matter_files` now runs every file, whole or cut, through one preparation path (`matter_files.prepare_local`, in the memory-capped child of `page_cut.py`, also used by the workspace page-finder check): it copies the pages (a whole file is cloned, outline and forms kept), deletes every `/AF`, `/EmbeddedFiles` and `/Collection` and every `/FileAttachment` annotation, and re-clones so the orphaned files are not written into the bytes. Nothing else is removed: a script, an action, a launch, an XFA form or a remaining file specification stays in the output, and the reply plugin's structural check and the broker refuse it exactly as before. An encrypted source refuses at staging. The child then counts the output's objects the way the reply check does, and a whole file past the bound is refused at staging with the instruction to stage a page range (a cut past it is told to ask for fewer pages), so the model re-stages instead of composing a reply that will be held. The staged bytes, and the sha256 recorded, are the rewrite, not the file as Smokeball holds it; the result names `embeddedItemsRemoved` when any went. This is the firm-own-file-to-own-staff path only: every other outbound file, and the broker's own checks, keep the full refusal of embedded files.

10. **Finding the pages in a scanned file** (amendment 2, 2026-11-02, after the first A&P run sent two of five records: three sat inside large image-only sets and the Operator had no way to see which pages held each one). `find_pages_in_file(matter_id, file_id, what, pages?)` (Smokeball connector, READ, fenced and tainting like `read_document`) splits the file into single pages in a memory-capped child (`page_split.py`), shows them to the seat's model a batch of 8 at a time, each page labelled in code, and asks only what is printed on it: each section that starts on the page (heading, type, date, provider; a canceled appointment is its own section, a "(continued)" header is not a new one), whether the top of the page continues an earlier section, and every labelled date on it. An answer that does not cover exactly the pages sent is refused, so evidence cannot move between pages. CODE then decides each section's pages from that index: a section runs until the next one starts, and a page where a new section starts mid-page belongs to both; positions are PDF positions, never printed page numbers. The index is cached per file sha256 at `/opt/data/smokeball-page-index/`, so a second request on the same file reads no page again. A text-only call then matches the colleague's words against those sections and names section ids per record asked for (only the named provider's sections answer a provider; a clinical note, never a canceled appointment, answers a date; a date printed only on a late page counts), or says what the sections show instead. Code turns the ids into page ranges and composes the evidence. Pages go whole. Header-and-footer strips were tried and lost on the real sets: the page still ships whole, so they saved about 9% of tokens, and mid-page headings went unseen. They stay behind `SMOKEBALL_PAGE_FINDER_VIEW=bands`. A page whose running header carries the note's label "(continued)" keeps that note open even when something embedded starts on it (a flowsheet, a report), so a long note is never cut short at its first embedded item. A "not found" over pages that were not read is reported as not established, never as none, and a refused response's input tokens count toward the cost. A batch the model declines is retried page by page; a page still declined is listed with its stop_reason, kept inside its section when the next page that was read continues that section (amendment 3), and `complete` stays false. Bounds: 100 new pages per call inside 200 s, the rest on the next call (cached pages are free), a 10,000-page runaway guard; tokens are tallied per call and per file. Cost at Opus 5.5 list price and effort low: about $0.90 per 100 pages indexed (an estimate from ~1,600 input and ~80 output tokens per page; every result reports the actual tokens). The same finder and the send-side checks run on a local copy with `python -m smokeball_connector.page_finder locate|check`, so acceptance on real files happens where those files already are.

11. **The reply's facts are written by code, from the finder** (amendment 3, 2026-11-02, an A&P records request: the Operator found the right files, but both replies it drafted retyped the finder's ranges and counts and got them wrong, dropping pp 48-49 and writing 59 for 57, and SMD wrote the one that was sent). The finder's result now carries every fact a reply states as fields code computed, versioned `schemaVersion: 2`: `counts` (`pages`, `read`, `unreadable`, `notReached`, which sum to `pages`), and per record the sections the match model names by id for `closest` (when not found) and `relatedCandidates`, which code turns into pages, heading and date from the index alone. No model sentence is carried into a reply; a not-established item's reason is code's, in lowercase, and the match model's own sentence stays in an internal field the tool never returns. A page the model could not read never extends a section by itself: the section bridges over it only when the next page that was read continues it, so a visit with an unread third page and a new visit on its fifth is 1-4 with page 3 named, never 1-5. A page that continues the note bridges the unread pages before it even when it also starts a section mid-page (then sharing that page with the new section); a page that only starts, and does not continue, never bridges them. And a truly empty page (no section, no date, no banner, label or page marker, and continuing nothing) belongs to no section, never extends one, and is never bridged; a page the model could not read that continues the note stays inside it and is listed as unreadable there, never ending it, because ending a note at a handwritten page would send a short record. A "(continued)" label keeps a note open past a new start on its page only when it names that note itself (its heading or record type): a record-level label such as "<record> Clinical Notes (continued)" names no note, so the note closes at the new start (the $0 replay on the seat's indexes: a 5/15 note ran 2-5 instead of 2-4, a discharge note 33-100 and 33-149 instead of 33-38, a speech note 48-51 through a blank page instead of 48-49), while a 35-page summary whose labels name it runs whole. The match is cached in the file's index under a hash of the model, the section lines, the unreadable pages, the normalised request and its own `MATCH_VERSION`, written only once every page has been tried (each read or recorded unreadable; a file with unreadable pages is the case the cache exists for), so the same question about the same pages gets the same answer; the page-reading prompt keeps the on-disk `version: 4`, so existing indexes stay valid and no page is paid for again. The reply plugin records each turn's `find_pages_in_file` result from its post-tool hooks and renders the facts block (`shared/matter_file_facts.py`): **Attached:** (each staged file by its name exactly as on the matter, which the reply checklist does not judge, its pages, the page count of the staged bytes, and the heading and date found on those pages), records possibly relevant but not attached (labelled candidates), records not found over every page, and records not established, with the counts and the closest sections. It goes into the body at the skill's `[[FILE FACTS]]` line (else after the opening paragraph) before the relay builds its scan text and html, so every gate and the review digest cover it; the model writes only the opening line, what could not be sent, and the open questions. The reply waits for SMD's review (never a redraft, which cannot fix what code wrote) when a staged range is not one the finder reported for that file, when a finder result is not `schemaVersion` 2 (an older connector, or a newer one than the overlay knows: no partial block is rendered), when the model's own words state a page or a count (`pp 48`, `page 5`, `12 pages`, `2,313 pages`; a number that is part of a document's name, such as `Exhibit 4 file`, is not a count) the facts do not, when a finder result and the staged files, or the session's content reads, are not all one matter, when the match named only sections the index does not hold (the record is then not established, never "not found"), or when only the facts block trips the reply checklist. On every such hold the marker is taken out and no partial block is written, and the body that would go is checked last: it never carries the marker, and in a turn that used the finder it always carries its facts block. A finder result is kept only with the email its turn answers, and matches only a reply to that email. And while `review` or `review_first` is on, every reply of a turn that called `find_pages_in_file` waits for SMD, files or not: before this, a records reply that attached nothing went past the review. A row held with no files is released as words alone, to the person it is for (a device's authored person on a redirect, which the broker re-checks); a reply that cannot be released that way (a seat whose transport is not Graph, a bound reply, a shared reply) is refused with its reason and the email closed, never held for a release that would go wrong.

12. **A records request is a queued job, never a turn's work** (amendment 4, 2026-11-03, after 11-02/03: every run inside the chat turn let the model choose which files to search, how often and with what words, twenty hours of guards each closed one observed failure before the next run failed a new way, and the last proof spent $17.06 against a $15 cap because nothing in a turn can stop spend). The turn now only queues: the router's records class calls `records_job_submit` (lane `records`, skill `matter-records`, REQUEST mode only), which takes the requester, the Graph message id and the sender's own words from the email that opened the turn (a forward submits nothing), and relays the broker's acknowledgement word for word, or sends no reply when that email already has a job (`already_queued`, `already_done`; a request is unique across every records job ever). A seat that does not author the lane answers in one fixed line and attaches nothing. The runner parses the request once (cached on its own words), resolves and downloads each file once, refuses before spending when the unread pages would pass the firm's per-job or monthly cap, calls the finder once per record and file with that record's own words until every page is tried (a cap reached mid-build keeps every page already paid for), cuts the reported ranges, and renders the facts from the shared contract `operator/connectors/_contract` (`records_contract.facts.render`, the same code the overlay's `matter_file_facts.build` now calls; the review row, its digest and the batches are the contract's too, so the gateway and the lane build the same bytes). The root lane spools the cuts into the broker, writes the review row (`session_id` `records:<job_id>`, owned by the gateway uid) and raises an ops card; the gateway's existing review sweeper sends it once SMD approves, exactly as a turn's row. Every verdict other than delivered, and every failure, holds for SMD; nothing is released without review while `review_first` lasts. `find_pages_in_file` and `stage_matter_files` are withdrawn from the connector's tool list on every seat, and the reply plugin refuses a stage call from a turn on a seat still offering it. The page index moves to the lane's own directory, `/opt/data/medchron/page-index`.

## Consequences

- The attorney's request is answerable: find each record by name, stage the whole file or the named pages, and the reply carries them, split across replies when there are more than three.
- A file over 3 MB depends on the shared upload-session helper. Until `workspace_broker/msgraph_upload.py` is on main, such a file refuses with a plain reason and the reply is held so the model says so; files under 3 MB go.
- Every send here runs inside the reply hook's 25 s broker budget. A large reply that outlives it is reported as an unknown outcome (the broker finishes and writes its row); the agent is told not to resend.
- The read credential builds the draft. Between the read-back and the send an agent holding that credential could in principle PATCH it; the window is one request long, the same stated property as the device-redirect path.

## Rejected

- **The vendor's `Search` index for finding files.** Unobserved matching and lag; a missed file reads as "not on the matter".
- **Files as a model tool argument, or bytes through the model's context.** The model names Smokeball ids; nothing it writes reaches the wire as a file.
- **Exempting scans by asking the model whether a file is a scan.** The exemption is keyed on who receives and where the bytes came from, both decided in code.
- **A new exposure class.** It would touch every validator and the portal for a question a recipients list answers.
