# The Operator: product model

Status: research draft, 2026-11-09. Built from code, config schemas, ADRs and the handbook in this repository, not from marketing copy. Vertical-neutral except section 15.

How to read it:

- Every claim carries a source: a repo path (line numbers where practical) or an ADR number. Paths are relative to the repo root. `OV/` means `operator/hermes-smd-overlay/`, `TRUST/` means `OV/plugins/hermes-smd-trust/`, `ROUTER` means `OV/plugins/hermes-smd-webhook-router/__init__.py`, `J/` means `operator/runners/jobs/jobs/`, `B/` means `operator/workspace_broker/`, `HB/` means `docs/handbook/`.
- Maturity uses three states: **IN PRODUCTION** (built and authored on the paying client seat), **BUILT, UNUSED** (merged; runs only on staging, the proving rig or SMD-paid seats, or is authored on no seat), **SPECIFIED** (decided in an ADR or spec, not built).
- Limit of this method: no live seat was probed. "In production" rests on what the repo authors and what the handbook states. Where the repo cannot settle a status, it is listed in section 16.
- Line numbers were taken on this worktree on 2026-11-09 and will drift.

## 1. Definition

The Operator is a managed AI worker that a business authors and SMD runs. Each client gets one isolated seat: a dedicated machine running an open-source agent runtime, wrapped in SMD's control layer, connected to the client's own systems and reachable over the client's ordinary channels (ADR 0007; `operator/CLAUDE.md:20-24`). It has no fixed function. What it does is authored per engagement across five surfaces: skills, entitlements, voice, connectors and memory, and anything not authored is refused (ADR 0037 Tenets 2-3; ADR 0035 §2). Every tool call passes a code-enforced gate that reads the authored entitlements; every action is written to a ledger the agent cannot rewrite (`TRUST/enforce.py`; `B/audit_ledger.py:1-19`). Multi-step or costly work runs as queued jobs with cost limits, independent review and proof of delivery (ADR 0103; `J/proof/`). SMD provisions, releases, monitors and changes the seat as a managed service; the client directs it, and where agreed moves its autonomy levels and pauses it from a management console that never shows client business data (ADR 0052). Commercially it is positioned against the next hire, with existing systems treated as connection targets (ADR 0037 Tenet 1).

### 4.3 States, holds and what the client hears

- Ledger states (most lanes): `submitted` or `queued`, `running`, `held`, `delivered`, `failed`. `delivered` is a dead end. Whether `held` can resume differs by lane (`B/medchron_ledger.py:61-89` versus `B/litigation_ledger.py:69-79`). Daemon-side terminal set adds `stopped_by_smd` and `observed` (`J/daemon.py:95`).
- Causes of a stop: unproven kind; review must-fix; cost cap, monthly budget or allowance; seat paused (job resumes itself when cleared); missing proof block; read-back mismatch; unusable firm inputs; infrastructure retries exhausted (4 in-place retries, `J/requeue.py:12-20`); SMD stop.
- There is no agent tool for stop, resume or accept (`J/stop.py:25-27`).
- When a job stops, the client is generally told nothing and SMD is paged once; a hold reply to the client is limited to fixed wording for the few hold classes whose answer is genuinely the client's (`B/stop_note.py:1-34`; `J/proof/holds.py:13-64`).
- Zero-cost rehearsals exist per lane and are distinct from a proof run: they replay saved inputs through deterministic gates against answer keys with no model call and no write (`J/medchron/rehearsal.py:1-27`; `J/litigation/rehearse.py:1-28`; `J/records/rehearse.py:1-27`). A proof run is not free: everything before the upload runs for real (`J/proof_mode.py:28-29`).
- Lanes: 8 (`J/lanes.py:24-33`). Two are general in shape (an SMD-approved note sent by digest; a staff request for named records answered with files through an SMD review row). Six are pack-specific (section 15).

## 16. Open questions and contradictions

### 16.1 Things the repo cannot settle (need a live probe or the Captain)

1. Which controls the paying client has actually exercised (confirm, send-as, Claude connector, level dial). The repo shows what is authored, not what was used.
2. State of the repo variables that gate controller releases, bundle rollout and spec signing.
3. Whether every seat runs on its own model-provider workspace key (`provision-customer.sh:533-544` prefers it; ADR 0010:23,64 calls the key a shared infrastructure secret).
4. Any model-provider retention period, zero-retention arrangement or processing region. None is documented.
5. Whether inter-machine private networking is closed: ADR 0007:42 says no network path between clients; `docs/security/operator-threat-model.md:195` still lists it as an item to confirm.
6. What a memory export contains today, and whether a client can see or delete a learned preference.
7. Whether agent skill authoring is live anywhere: ADR 0017 keeps `skill_manage` enabled; `action_classes.py:997` classes it `code_execution`, which no seat authors.
8. Whether the staging dry run of offboarding was done (`HB/customer-lifecycle.md:158` says it is not recorded).
