This page explains how the Operator is built: the runtime it sits on, the code SMD owns, and how each client's seat is kept apart from every other. An administrator needs it when an agent's report about a seat, a boot failure or a document format sends you here.

## What the Operator runs on

The Operator is not a system we wrote from scratch. It runs on the **NousResearch Hermes Agent** runtime (MIT-licensed), and the code SMD owns is a thin **plugin-only overlay** that extends Hermes through its documented extension surface. This is the single most important fact about the platform: Hermes is the substrate, and almost everything an agent does - the LLM loop, skills, memory, the tool registry, approval and guardrail machinery, MCP integration - is native Hermes, not SMD code. The architecture was substantially realigned on 2026-05-24 after six rounds of focused research, and that realignment is what this page describes.

Three principles govern all Operator work. They are not aspirational; they decide what gets built and where the code lives.

1. **Hermes is the substrate. Trust it.** Skills, memory, the tool registry, the plugin hook surface, MCP integration, and approval machinery are native and not reinvented. Teknium's (the Nous Research lead) May 2026 hard rule applies: plugins MUST NOT modify Hermes core files (per ADR 0015, citing upstream `AGENTS.md`).
2. **Build only what Hermes won't.** Sample-driven voice transformation, compliance-grade audit emission, content-class trust ceilings, configurable send-posture routing, curated vertical skill catalogs, and the customer-facing business surface are what we build on top of Hermes. None are on its roadmap.
3. **Mirror, don't gate.** Where Hermes' learning loop creates state, the overlay captures a parallel record with provenance in Machine-local SQLite on the seat's own Fly volume (ADR 0062 records that the per-customer D1 originally named here was never built), so the Captain can inspect and reverse it. No approval queue stands between the agent and its work; safety is enforced by authored entitlement ceilings (see `/admin/playbook/autonomy-governance`), not by an interposed gate.

## The fork posture: pin, don't patch

SMD does not maintain a modified Hermes. Per ADR 0015 (the plugin-only half, which stands; the fork half was superseded by ADR 0024), SMD pins Hermes at a specific upstream tag and SHA and runs it byte-for-byte. The pin lives once, as `ARG HERMES_UPSTREAM_TAG` / `HERMES_UPSTREAM_SHA` in `operator/templates/Dockerfile`, and every seat runs the shared fleet image built from it; the per-seat `hermes_ref` field was retired from `customer.yaml` in #3332 and the validator now rejects it. All SMD-specific runtime code is the MIT-licensed overlay at **`operator/hermes-smd-overlay/`** in this repo. Until 2026-10-22 it was the separate repo `venturecrane/hermes-smd-overlay`, pinned into the image by `OVERLAY_REF`; ADR 0095 folded it in, so the image is built from one tree and the version a seat reports is the ss-console commit it was built from. The fold moved where the code lives, not what it may touch: it is still plugin-only.

Why this matters: Hermes ships at high velocity (ADR 0015 cites 459+ PRs per week and 13 minor releases in 10 weeks). A hard fork would impose prohibitive maintenance cost on a single-Captain venture. By keeping all our code in the overlay and never touching core, a Hermes upgrade becomes a tag-bump exercise rather than a code-merge exercise, and our rebase cost approaches zero. The overlay ships as a set of narrow Hermes plugins (29 under `operator/hermes-smd-overlay/plugins/` on 2026-11-09, among them audit, trust, voice-notes, memory-mirror, peer-memory, corrections, inbound, drafting, and record-store) plus a `shared/` support package, a `bootstrap/` CLI, four root-owned appliers (`config_applier/` for `customer.yaml`, `spec_applier/` for the client's authored voice and format specifications, `skills_applier/` for skill releases, `firm_inputs_applier/` for the lanes' firm inputs), the root `establish_intake/` daemon, and `webhook_gate.py`. Each plugin registers against Hermes' documented lifecycle hooks (`pre_tool_call`, `pre_llm_call`, `transform_tool_result`, `on_session_start`, `on_session_end`, `pre_gateway_dispatch`, and others).

The proprietary value is deliberately not in the hook code. It is in the SMD backend: the audit database, voice training, the admin console, and customer onboarding. Open-sourcing the overlay costs us nothing and signals craft (ADR 0015).

## One Machine per customer

Per ADR 0007, each customer gets a dedicated **Fly.io Machine** named `hermes-{customer-slug}`. There is no shared runtime across customers. Multi-tenancy is achieved through deployment isolation, not runtime tenancy.

This is a deliberate trade against the standard SaaS pattern. For an Operator working inside a regulated practice (the first vertical is personal-injury law, but the principle holds for every regulated vertical the platform will ship into), the cost of cross-customer data leakage is unbounded: privilege breach, bar discipline, an existential lawsuit. So the isolation guarantee is placed in the deployment topology rather than in application code. Customer A's Machine has no network or storage path to Customer B's data. Cross-customer access is not "denied by code" - it is architecturally impossible (ADR 0007).

Each customer's Machine carries:

- Its own Fly volume at `/opt/data`, which holds the seat's state as Machine-local SQLite (the broker-owned audit ledger at `/opt/data/audit/audit.db`, the agent-state database at `/opt/data/agent-state.db`) plus connector tokens and profile homes. It also holds two caches of transcribed matter-document text that survive reprovision by design: the Smokeball extraction cache (`/opt/data/smokeball-extract-cache/`) and the litigation lane's text cache (`/opt/data/jobs/litigation/textcache/`, one entry per file content, reused by later lists so a page is paid for once). A matter removed from a seat is purged from the second with `python -m jobs.litigation.textcache purge --matter <id>` (`operator/runners/jobs/jobs/litigation/textcache.py`). Text is reused only while the way it is made is unchanged: a change to any extract reader must bump `EXTRACT_VERSION` in `operator/runners/jobs/jobs/litigation/extract.py`, or text made the old way keeps being served. The case file manager reads through the same text cache, and keeps its own state of client facts (what each matter's last File Status said) at `/opt/data/jobs/casefile/state/`, from which a removed matter is purged with `python -m jobs.casefile.state purge --matter <id>` (`operator/runners/jobs/jobs/casefile/state.py`). A seat that authors the sealed web reader (`connectors.WebSearch.sealed_reader: true`, ADR 0099) also keeps `/opt/data/research/research-log.jsonl`, one line per `web_research` call carrying the question asked, the mode and the item counts; it holds no page text, and a seat's removal is not complete until it is gone with the volume (`operator/hermes-smd-overlay/shared/sealed_reader.py`). A seat that runs combined post intake keeps `/opt/data/post-intake-journal/`, one record per scanned bundle (page ranges, senders as printed, matter numbers and message ids, never page text) plus the numbered daily post lists sent from it, each kept 45 days (`operator/connectors/smokeball/smokeball_connector/post_journal.py`). The per-customer D1 and Vectorize bindings (`hermes-{slug}-d1` and so on) in the original design were never built: no provisioning code creates them and none exist in the account (`operator/migrations/README.md`; ADR 0062).
- A per-customer R2 bucket for agent-authored skill bodies, `ss-operator-{slug}-skills`, created by `operator/bin/provision-customer.sh`. Its `customer.yaml` lives in the shared `smd-customer-config` bucket under a per-slug key, and the nightly audit export goes to the shared, object-locked `smd-audit-archive` bucket under `audit/<slug>/` (`operator/bin/audit-chain-watch.py`).
- The shared fleet image, so a Hermes upgrade reaches every seat through one Dockerfile pin rather than a per-seat re-pin.

A **boot-time invariant** enforces this: as the first of two root gates before the privilege drop (the second checks that the authored-spec tree is not writable by the agent), `operator/templates/entrypoint.sh` runs `operator/safety_substrate/invariants/invariant_7.py`. It checks that the skill-bodies bucket is exactly `ss-operator-{slug}-skills`, that the shared config bucket does not point at another seat's skill bucket, that the on-volume SQLite paths resolve inside `/opt/data` and name no other seat's slug, and that the runtime's and the overlay's slug variables agree. It exits 3 (refusing to boot) on a violation or if the module is missing (safety invariant #7; ADR 0009, wired 2026-07-13 under SEC-22). The accepted cost is that operational complexity scales linearly with customer count - the control plane must provision, monitor, update, and decommission one Machine per customer, and each Machine carries a baseline cost even when idle (ADR 0007).

## Where a seat's connector credentials live

ADR 0010 placed a customer's own OAuth tokens on that customer's Fly volume, never in Infisical and never in a shared store, and ADR 0036 fixed the on-disk shape for Google as the google-auth authorized-user JSON. The principle stands (a customer's credential stays inside that customer's Machine), but where each credential sits has moved since:

- **Google Workspace** credentials are held by the workspace broker, not the agent (ADR 0045). At each boot the entrypoint deletes any `/opt/data/oauth/google.json`, materializes the credential from the seat's Fly secrets into the broker's own directory (`/var/lib/smd-workspace-broker`, mode `0700`, owned by the broker user), then unsets every `GOOGLE_*` variable before the agent process starts (`operator/templates/entrypoint.sh`; `operator/workspace_broker/google_auth.py`). The agent reaches Google only through the broker's socket.
- **Smokeball** consent lands on the seat's own Machine (ADR 0054), and the refresh token lives on the volume at `/opt/data/.smokeball-mcp/refresh_token`, group-restricted to the processes that need it (`operator/templates/entrypoint.sh`; `operator/connectors/smokeball/smokeball_connector/client.py`).

SMD owns the shared infrastructure secrets (the model API key and similar); they stay in Infisical and are pushed to each Machine's Fly secrets at provision time (`/admin/playbook/secrets-access`). ADR 0010 also describes an `oauth.token_read` audit event on every token read; no code emits it today. Decommissioning a seat deletes its volume and with it the tokens stored there (ADR 0010; `operator/bin/decommission-customer.sh`).

## A persona is a Hermes profile

When a customer wants more than one AI identity - say an inbox-triage operator and a separate intake handler running against the same firm's connectors and memory but with distinct signature blocks and skill assignments - that is modeled as **multiple Hermes profiles**, not multiple Machines and not an in-process dispatcher (ADR 0011). A persona maps cleanly onto a Hermes profile: each profile has its own `HERMES_HOME`, `SOUL.md` identity file, `config.yaml`, skill catalog, and memory peer card. Profiles are Hermes' native unit of identity isolation.

ADR 0011 shipped v1 at `personas[]` length 1. The validator today requires at least one persona and at least one with `status: active`, and sets no upper limit (`src/lib/operator/customer-yaml/sections-personas.ts`); every seat in `operator/customers/` still authors exactly one. Persona switching mid-session uses Hermes' native `/handoff` command. The decision explicitly does not spawn a Machine per persona (that would multiply cost and fracture the shared-memory story) and does not modify Hermes core to run personas concurrently in one session (Hermes does not support this and is not building it) (ADR 0011).

## How customer.yaml becomes a running profile

The bridge between the SMD product surface and the Hermes runtime is a translation step. SMD authors a `customer.yaml` (storage and authoring covered in `/admin/playbook/knowledge-memory`), which speaks the product's vocabulary - customer, persona, connector, entitlement. Hermes speaks a different vocabulary - profile, model, MCP server, personality file. The `hermes-smd bootstrap` CLI in the overlay performs that translation at Machine startup (ADR 0019).

For each persona, bootstrap creates the profile directory, writes `SOUL.md` (identity, tone, escalation rules) and `config.yaml` (model pin, memory config, MCP server bindings from `connectors{}`, the overlay plugins enabled with their per-plugin config), and copies the persona's enabled skills into the profile's own `skills/` directory, removing any it no longer enables (overlay `bootstrap/translate.py`). The translation is deterministic (same input produces byte-identical output) and idempotent (re-running it changes nothing). After boot, changes reach the running seat through the overlay's root-owned `config_applier`: a merged `customer.yaml` is published to R2 by the deploy workflow (`.github/workflows/deploy.yml`), and the applier polls that object every 15 seconds by default, validates it, and applies only fields on its live-writable allow-list (entitlement ceilings and similar), with no reboot (ADR 0044; overlay `config_applier/__main__.py`). Rebuild-class fields are rejected on the live path and take effect at the next boot or re-provision, so OAuth tokens on the volume are never disturbed (ADR 0019). The `customer-sync` sidecar the original design named was never built; the applier is what replaced it. The deploy publisher is the only writer of that object; the nightly reconciler only reads it and pages, and provisioning uploads through the same compiler (ADR 0094, amended).

## Firm inputs adopt live

Each job lane reads its firm's configuration from `/var/lib/smd-config` on the seat: the demand, drafting, litigation, case file and records inputs (one directory each, marked by `<lane>-firm.yaml`) and the chronology lane's `medchron-firm.yaml`. They come from the vault (`vaults/<slug>/<lane>/`, and `vaults/<slug>/medchron-firm.yaml`). A correction to one of them used to reach a seat only at its next boot. Now a published change reaches the running seat within about a quarter of a minute, with no restart and no reprovision.

The shape. Each lane's live path is a symlink to a versioned copy named for the first 8 hex characters of its marker object's ETag, for example `records -> records.v1a2b3c4d/` and `medchron-firm.yaml -> medchron-firm.v1a2b3c4d.yaml`. The boot fragments (`operator/templates/entrypoint-fetch-inputs.sh` and each lane's file) fetch into a staging copy, own it root:jobs, validate it with the runner's own validator from the jobs bundle, and only then swap the symlink in one rename. After boot, the root `firm_inputs_applier` (a loop in the one root poller process, `operator/hermes-smd-overlay/firm_inputs_applier/`) checks each authored lane's marker in the vault every 15 seconds (`SMD_FIRM_INPUTS_POLL_SECONDS`) and adopts a changed one the same way, refreshing the broker's copy of the litigation, case file and records configuration before the swap. A job resolves the symlink once when it starts (`operator/runners/jobs/jobs/firm_inputs.py`), so a job already running finishes on the version it started with. The newest three versions are kept.

What can and cannot happen. A copy the validator refuses is never swapped in: the live copy stays, the lane's state reads `rejected` with the validator's first line, and that version is not retried until the vault changes again. A validator that cannot run never replaces a working copy. Only lanes the seat authored at boot are watched (`SMD_AUTHORED_LANES`); a lane newly enabled in `customer.yaml` still needs a boot, and inputs deleted from the vault leave the seat at its next boot.

How to confirm a publish landed. The applier writes `/run/smd-firm-inputs/state.json`, the heartbeat carries it as `firm_inputs` (migration 0149), and `fleet status` shows each lane's version in its `firm inputs` column, with `(refused <version>)` on a lane whose newest publish was refused. Compare it with the marker's ETag in the vault. The seat self-test check `jobs-firm-inputs-current` fails if a lane's symlink and the state disagree. The state file is world-readable because the heartbeat runs as the agent user; the validator's own words for a refused version stay root-only beside it, in `/run/smd-firm-inputs/<lane>.rejected`.

### The firm's attorney roster

Who a firm's attorneys are is written down once, in the firm's `attorneys.json`, a firm input like the lanes' (`vaults/<slug>/attorneys/`, installed at `/var/lib/smd-config/attorneys/`). It lives in the private engagements repo at `operator/customers/<slug>/attorneys/attorneys.json` because it names the firm's staff; `operator/customers/_template/attorneys/attorneys.json` shows the shape with made-up people. Each entry is one attorney: the name exactly as the case system gives that staff member, their emails, their bar number, their caption block, and how they sign a demand and a form letter. Staff who sign form letters and are not attorneys are listed separately and are never an attorney for anything else. The one reader is `operator/connectors/_sdk/operator_connector_sdk/library/roster.py`; the publish and the applier validate a roster with `python -m jobs.attorneys.firm`.

Every path that names an attorney reads it: the drafting job's caption block, the demand's signature, the form letters' signers, the library resolver's attorney, and "set up Dana's memos". A seat with no roster installed reads each lane's own list exactly as before (the drafting inputs' `attorneys`, the demand inputs' `attorneys`, `customer.yaml`'s `form_letters.signers`). Once a roster is installed it wins, and the self-test check `attorney-roster-agrees` fails, which pages SMD, for every way a lane's own list still says something else. With a roster installed, a job whose matter names a responsible attorney the roster does not list as an attorney holds before anything is paid and the firm is told why (`attorney_not_rostered`); a roster that cannot be read stops every one of those paths for SMD, never read as "nobody". To draft a firm's first roster, run `operator/runners/jobs/tools/draft_attorney_roster.py` in that firm's ops workspace: it lists the case system's staff and the three lists, and prints a draft for SMD to review before it is committed.

## Documents come back in the firm's format, and the format lives in Word

A drafting skill files work product as a real Word document through the Smokeball connector (`mcp_smokeball_render_docx_draft` with a `document_class`), and the connector renders the content into the firm's own Word template for that class when the firm's Document Library holds one (resolved deterministically from `self_initiation.document_library` in `customer.yaml`: the library matter by number, the folder by name, the file by the class's name), else onto a Times New Roman starter with the named styles defined. Letterhead, page setup, fonts, spacing, item labels, headings, caption tables, and page numbers are the renderer's; the model writes content only, including the labels' own numbers, the caption, the signature block, and the proof of service, and the renderer adds no text. Typography is not config: the firm edits a style in Word and the next draft follows, with no publish and no reboot. The establishment turn (`operator/skills/document-library-establishment/SKILL.md`) no longer builds templates: since 2026-11-09 it routes every "set up the document library" to the library setup job below, which covers the five kinds the drafting job makes of the seven classes the renderer knows (`discovery_set`, `discovery_response`, `demand_letter`, `mediation_brief`, `memo`, `depo_outline`, `letter`; `operator/connectors/smokeball/smokeball_connector/docx_classes.py`). A demand letter is already written from the firm's own demand, and a letter is not part of the setup. The Operator's own starter templates are retired; the starter remains only as the renderer's base when a kind has no file of the firm's. The letterhead on a `letter` or `demand_letter` is never model text: the firm's own template file for the class supplies it when one resolves (a class template the Operator filed from the SMD starter, recognized by the marker the starter writes into its document properties or by its named styles, is not the firm's file for this purpose and takes the authored letterhead while its header is empty), else the renderer prints the firm's identity authored once in `customer.yaml` (`firm_identity`: `name`, `street`, `city_state_zip`, `phone`, `fax`, `website`; only the name is required and an absent field is an omitted line) into the starter's first-page header, where it survives into every later draft rendered into that template, and else the report says there is no letterhead; nothing is ever markered in its place. Memos carry none, and a pleading's firm block stays content beneath the per-document attorney line (`operator/connectors/smokeball/smokeball_connector/letterhead.py`). A firm document that is none of the seven (a retainer, an intake form) can be filed as an additional reference template under its own name; it is never a format base, and the render tool refuses a classless template under a class's name. The template gate also refuses a `{{FILL}}` marker that does not name its source (ADR 0083, 2026-08-19 amendment; `operator/connectors/smokeball/smokeball_connector/docx_format.py`, `render.py`, `library.py`).

## "Set up the document library" finds the firm's own files

An administrator asks the Operator to set up (or refresh) the document library, which "Initialize yourself and set up for our firm" includes, or one kind of it ("set up our discovery responses"), or one attorney's ("set up Dana's memos"). The turn queues a job on the drafting lane (`library_setup_submit`, `operator/workspace_broker/library_setup_verbs.py`) that runs no model. For the whole library (`kind: library`) it lists the firm's matters once and hunts every kind the drafting job makes (discovery sets, discovery responses, mediation briefs, memos, deposition outlines; the California names a firm files them under are in `firmbase/hunt.py` `RULES`), and replies with one numbered list per kind, the recommended one first and then newest first, how many of the firm's own it found, and which file each kind uses now (the file the firm chose before, a file the firm's drafting inputs pin, or the standard format); kinds with nothing found keep what they use. For one kind it reads that kind only. A request may also point at a document by its matter number or by words of its name, which must appear in the request's own words, and the job then reads only that (`hunt.pointed`). Each listed document is one the library file can actually be made from (`library_setup/plan.py` `contract_for`): a mediation brief or memo through its marked plan where the document fits it, else, and for the other three kinds always, as a styles base (`styles_make.py`), the whole make run with the firm's identity and nothing written; a document neither can make is not listed and is counted by its reason (`operator/runners/jobs/jobs/library_setup/`). An attorney is matched against the attorneys the firm's drafting inputs list, each mapped to the name the case system gives them; one not on that list, or a name that fits two, is said to the firm, and a list that cannot be read holds the job for SMD. Behind the seat's `logic_in_code.library_setup` switch: off, which is every seat until it is switched on, the job only counts, the firm hears nothing from it, nothing is written anywhere, and the request is answered as it is today. On, the firm is sent the candidates and asked which to use, in the words of `operator/workspace_broker/library_setup_wording.py`, the one file every such sentence lives in. The administrator answers in the thread, one line per kind on the library's lists ("discovery responses: use 2", "memos: keep the current one", "memos: use the one on matter" and its number, or a quoted document name), or any line on a one-kind list. Code reads every choice from the reply's own words (`library_setup_choose`, `read_acts` in `operator/workspace_broker/library_setup_choose.py`): the sender must be a Named Administrator and the person who asked, the reply must be in the lists' thread, each kind must get exactly one listed number, file id or listed matter (or "keep"), and each list must be the newest for its kind and attorney. A matter or a name not on the list queues a new list of what was pointed at, in the same thread. A chosen kind gets its own accept job, carrying the contract the list named. Anything else is refused in a sentence from the wording file and nothing happens. A chosen document is made into the library file by the drafting lane's job (`operator/runners/jobs/jobs/library_setup/accept.py`, `make.py`): the kind's marked plan, or the styles base for a `styles` choice, takes every word of the case out and keeps the look, custom XML parts are dropped, and a header or footer line may remain only when it is page numbering, the firm's own identity from `firm_identity` and its authored attorney blocks, or a document-title phrase. The file is filed in the firm's Document Library on the library matter (`file.py`, one `add_file` or `add_file_version` and no other write), then handed to the root writer (`library_setup_accept_submit`, with its contract `marked` or `styles`; never `prototypes`), which runs its own no-client-text check, writes the vault and waits for the applier (`establish_intake/library_accept.py`, dispatched by the intake). The next draft of that kind is made in the new file and records it in `library-resolution.json`. A switched-on seat's setup jobs write `LIBRARY_SETUP_*` audit rows, whose portal lines are in the same wording file. The rehearsal is `operator/runners/jobs/tools/library_setup_rehearse.py`; `--kind library` runs every kind's hunt and lists exactly as the job does, and `--accept-dry` runs the accept job's checks at no cost and files nothing.

## A rule the firm confirms reaches the documents its jobs make

A firm says a rule about its documents ("never cite the medical records in a brief"), the Operator reads it back, and on a yes the seat records it. The read-back covers only the kinds of document the person's own message names, and an attorney only when they are that attorney or name them; code checks that against their words and the model cannot widen it (`operator/hermes-smd-overlay/shared/rule_reach.py`). The root spec applier writes each such rule, with its kinds and attorney, to `classes/work_product/wording.json` beside `layout.json`, under the same root-computed manifest (`shared/wording_rules.py`). The drafting and demand jobs read it once at job start, keep the rules for the job's kind and the attorney the matter record names, and put them into what they send the model when composing and repairing (`operator/runners/jobs/jobs/firm_wording.py`). The install letter says "in effect" only for a kind a job reads; a letter, a chronology or a workbook still gets "recorded" and SMD is paged. All of this is behind the seat's `logic_in_code.wording_rules` switch: off, which is every seat until it is switched on, the jobs send exactly what they sent before and the letter says "recorded". On, an installed store the seat cannot trust holds the job for SMD before anything is paid. A rule confirmed before the reach was recorded has none, so no job reads it until the firm restates it. A layout rule follows the same reach: switched on, it is compiled into `layout.json` for exactly the kinds it recorded, never for every kind, and a rule that records none is refused at install (`shared/layout_reach.py`). Layout rules already installed keep the kinds they were compiled with; `layout_reach.unscoped_report` lists the ones whose own words name no kind, to read before a seat is switched on.

When a layout rule and the firm's own library Word file disagree, one order decides (`operator/runners/jobs/jobs/drafting/layout_precedence.py`): what a court rule requires comes first (on pleading paper, the line pitch, and the margin floors of rule 2.107), then the later of the firm's rule and the firm's own saved edit of its accepted library file, because both are the firm's word. A rule that a later edit changed is recorded as replaced by that edit, with its version and date, in the `layout_precedence` block of `library-resolution.json`. An edit the library ledger cannot place against a rule leaves the rule standing and pages SMD (`layout_rule_unplaced`). This acts only on a document made in an accepted library file whose current version is the firm's own edit. Writing a rule into the library file itself, as a new version the ledger records as written by code, is behind `logic_in_code.layout_into_library` (`operator/runners/jobs/jobs/drafting/layout_into_library.py`): off, the job records what it would write and the rule is laid onto each document as before. The rehearsal's `--layout` step prints, for a seat's installed rules and an accepted file, each property's winner and whether the format check holds it.

## Spreadsheets are read as cells and built in code

The Operator reads an Excel workbook (.xlsx) the way it reads any other document: `read_document` on a matter and `read_attachment_text` on an emailed attachment return each sheet as a `## Sheet:` block with one row per line. A formula the file never computed reads as `[formula, no saved value]`, never as a blank that could pass for zero. Legacy .xls files, encrypted Office files, and PowerPoint decks are refused by name. It builds a workbook with `mcp_smokeball_add_workbook`: the model supplies typed columns and rows as data, and the connector writes the file, sums any `totals` columns itself, reads every cell back against the input before uploading, and files it on the matter. A text cell is always text, so a value beginning `=` is never a formula. Every workbook it builds is stamped as the Operator's, and the drafting record check skips those, so the Operator's own figures never count as the firm's record. A spreadsheet is readable but is never staged as a vendor invoice (`operator/connectors/smokeball/smokeball_connector/xlsx_io.py`, `workbook_tools.py`).

## The system, not a feature

The platform is best understood as three compounding layers, and the moat is the combination, never any one piece (ADR 0037, Tenet 4):

- **The harness** - configurable trust enforced in code: what the operator may do, who it may contact, what requires escalation.
- **The guide** - the human who authors `customer.yaml` well for a specific business, plus the authored knowledge itself.
- **The memory** - the per-customer operating memory that deepens over time and raises switching cost.

Calling any single feature "the moat" - voice fidelity, audit, draft-for-review send - is a category error. Competitors will have configurable agents; they will not easily have the guide or the accumulated memory. The autonomy and trust machinery is detailed in `/admin/playbook/autonomy-governance`; the three knowledge lanes in `/admin/playbook/knowledge-memory`; the connector and channel surface in `/admin/playbook/connectors-channels`.
